## 1. 输出目录

默认输出到仓库根目录 `docs/project-insight/`。扫描报告、符号索引、临时分析结果放入 `_analysis/`，不要混入最终学习文档。

## 2. 必须生成的文档

完整分析至少生成以下 11 份 Markdown：

| 文件 | 内容与用途 |
|---|---|
| `README.md` | 文档导航、项目定位、建议阅读顺序、分析范围 |
| `00_项目总览.md` | 项目目标、应用场景、功能边界、技术栈、依赖、构建与运行入口 |
| `01_目录结构与文件功能索引.md` | 目录树、文件清单、逐文件职责、重要类/函数入口、排除项 |
| `02_系统架构与模块关系.md` | 分层架构、模块职责、依赖方向、接口、进程/线程关系 |
| `03_核心执行流程与数据流.md` | 启动流程、关键业务链路、数据流、状态流、异常路径 |
| `04_核心算法与技术原理.md` | 项目实际使用的算法、原理、参数、假设、替代方案、局限 |
| `05_项目快速学习指南.md` | 学习顺序、重点文件、前置知识、动手验证、阶段目标 |
| `06_面试知识点总结.md` | 面试考察优先级、原理、项目映射、工程问题和掌握程度 |
| `07_项目面试题.md` | 选择/填空/简答/开放论述/系统设计/算法设计/排障/AI 协作题，按需选择题型 |
| `08_项目面试题答案.md` | 每题答案、推理过程、项目证据、追问、常见误区和出题意图 |
| `09_项目思维导图.md` | Mermaid mindmap，并可补充架构图或流程图 |
| `10_分析覆盖与待确认项.md` | 已分析范围、未分析范围、排除项、证据等级、风险和后续建议 |

题目数量由知识点数量和重要性决定，不设固定上限。不是每个知识点都必须出算法题；不适合算法题的领域应增加原理讲解、设计讨论和故障分析题。

## 3. 统一写作规则

- 默认中文，技术术语保留常见英文名，首次出现时解释。
- 默认采用清晰的自然段；对比、参数、文件索引、题目元信息适合用表格。
- 先讲结论，再讲原因、原理、项目中的具体实现、适用范围和局限。
- 不要只堆类名、函数名或术语；说明它们在系统中解决什么问题。
- 对关键结论提供源码路径和符号定位。行号仅在已确认时写，不得猜测。
- 区分“项目已经实现”“项目文档声称”“建议改进”“尚未验证”。
- 不确定内容明确标记 `待确认`，不要用流畅文字掩盖证据不足。
- 代码片段应短小、可读，保留真实接口名；不要凭空创造项目中不存在的类或参数。
- 若项目规模太大无法逐个深读，仍应完整列出清单，并说明哪些文件仅做了索引。

## 4. 图表与思维导图

使用 Mermaid，保证语法可渲染。至少提供项目知识 mindmap；如果项目有多个关键执行链路，再增加 flowchart 或 sequenceDiagram。

图表必须使用真实模块名和已确认关系。建议图例区分调用、数据传递、控制依赖和运行依赖。未知关系不要画成确定连线。

思维导图应包含项目目标、系统架构、主要模块、核心算法、数据流、工程实践、测试验证和面试知识。不要直接套用固定机器人模板。

## 5. 文件索引覆盖规则

对项目自有、与理解和运行相关的文件，尽量逐文件列出：路径、类型、功能、重要程度、关键符号、关联模块和分析状态。

文件重要度建议分为：

- `P0 核心`：入口、关键算法、核心数据结构、控制/状态管理、关键接口。
- `P1 重要`：配置、通信、硬件抽象、启动部署、测试。
- `P2 辅助`：通用工具、日志、可视化、数据转换。
- `P3 外围`：示例、文档、低频脚本、非核心资源。

第三方源码、生成代码、构建目录、缓存、模型权重、数据集和大型二进制资源可按类别或目录统计，不要求逐个阅读内容；若它们影响运行，应说明其作用和入口。敏感文件内容不得读取或复制。

## 6. 完成检查

最终检查以下问题：

- 项目总览中的技术栈和入口是否有证据？
- 文件索引是否区分了自有源码、第三方和生成文件？
- 架构图是否与实际调用/数据流一致？
- 执行流程是否覆盖启动、主流程和输出？
- 算法说明是否包含假设、参数、局限和验证方式？
- 学习指南是否告诉读者先看哪些文件、为什么？
- 面试题是否覆盖本项目真正有价值的知识，而不是机械地每个函数一题？
- 答案是否与题目一一对应，是否包含项目证据？
- 思维导图是否反映真实项目？
- 是否明确写出未读文件和待确认项？
