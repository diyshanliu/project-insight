## 1. 分析前：确定项目边界

先确认当前工作目录、仓库根目录、项目说明、开发规范和已有文档。检查 `AGENTS.md`、`README*`、`CONTRIBUTING*`、`docs/`、`CMakeLists.txt`、`package.xml`、`pyproject.toml`、`setup.py`、`Cargo.toml`、`package.json`、Docker 文件、CI 配置等。

若项目包含子仓库、Git submodule、多个 package 或多个可执行程序，先明确边界。不要把工作区中相邻但无关的目录混为一个项目。

检查 Git 状态只是为了保护用户工作区，不要擅自 stash、checkout、reset、clean 或覆盖文件。存在未提交修改时，记录它们并避免触碰。

## 2. 先建立项目地图

执行 `scripts/scan_project.py`，获得目录、文件类型、大小和路径索引。再按用途分类：

| 类别 | 常见内容 | 分析重点 |
|---|---|---|
| 入口与启动 | `main`、CLI、ROS node、launch、service | 谁启动、初始化什么 |
| 核心源码 | `.cpp/.hpp/.py` 等 | 类、函数、算法和状态变化 |
| 公共接口 | 头文件、消息、服务、Action、API | 输入输出、契约、依赖 |
| 配置 | YAML、JSON、参数文件 | 参数含义、默认值、覆盖关系 |
| 构建与依赖 | CMake、package manifest、requirements | 编译目标、依赖边界 |
| 测试 | unit/integration/system tests | 如何验证功能和边界 |
| 部署 | Docker、systemd、脚本、交叉编译 | 运行环境与启动方式 |
| 资料与资源 | README、设计文档、URDF、模型 | 项目约束和资源关系 |

目录名只能作为初始线索。一个叫 `planner` 的目录不一定承担完整规划功能，必须读代码确认。

## 3. 还原程序运行链路

优先回答“程序从哪里开始、经过哪些步骤、最后产生什么结果”。

建议按以下顺序追踪：

1. 可执行目标和入口函数：`main()`、Python `if __name__ == "__main__"`、CLI entry point、ROS node/component。
2. 初始化：参数读取、配置加载、日志、线程、通信、硬件连接、模型加载。
3. 主循环或回调：定时器、订阅回调、消息队列、任务调度、训练迭代。
4. 核心计算：数据预处理、状态估计、算法调用、决策、控制或输出。
5. 结果出口：Topic、Service、Action、网络接口、文件、硬件总线、可视化。
6. 异常与退出：超时、重连、异常捕获、资源释放、急停和安全状态。

不要只根据函数名推断执行顺序。确认调用关系、回调注册、线程启动、状态机跳转和配置选择。

## 4. 还原模块关系与数据流

对每个重要模块说明：职责、输入、输出、依赖、被谁调用、调用谁、关键状态、运行频率或触发条件、失败时的表现。

区分以下关系：

- **调用关系：** A 函数直接调用 B 函数。
- **数据关系：** A 产生的数据被 B 消费。
- **控制关系：** A 决定 B 何时运行或切换状态。
- **构建依赖：** A 编译或链接时依赖 B。
- **运行依赖：** A 运行时需要 B 服务、进程、设备或模型。
- **配置关系：** 配置文件决定模块参数或模块启用状态。

图中使用不同连线或图例表达不同关系，避免一张图把所有关系混在一起。

## 5. 深入分析核心文件

核心文件优先级通常为：程序入口、核心接口/数据结构、算法实现、状态机/调度、配置加载、硬件/传感器接口、通信接口、测试。

分析每个核心文件时，回答：

- 文件职责及边界是什么？
- 关键类、函数、成员变量和状态是什么？
- 输入从哪里来，输出交给谁？
- 关键参数、单位、坐标系、时间戳和生命周期是什么？
- 关键算法如何工作，为什么这样设计？
- 复杂度、实时性、内存或线程方面有什么约束？
- 哪些错误或边界情况可能发生？
- 项目如何测试或验证？

普通工具函数只需简述，不要为了“逐文件解释”而堆砌低价值内容。

## 6. 证据与置信度

对重要结论尽量附上 `相对路径:行号`、类名或函数名。推荐使用以下标签：

- `源码确认`：可以在实现、调用或配置中直接找到证据。
- `文档说明`：项目文档明确描述，但尚未由实现交叉验证。
- `工程推断`：根据多个代码事实推断，需说明推断依据。
- `待确认`：缺少代码、运行环境或外部系统证据。

如果代码与 README 不一致，分别记录，不要擅自选择一个版本当成事实。

## 7. 大型项目的分批策略

当文件量大、上下文不足或包含多个子系统时，分层分析：

**第一轮：** 全局清单、构建目标、入口、子系统边界。

**第二轮：** 每个子系统分别追踪接口、核心类和执行链路。

**第三轮：** 跨模块数据流、线程/进程关系、配置覆盖、部署关系。

**第四轮：** 汇总架构、算法和面试资料。

每轮都记录已读文件、未读文件、排除原因和待确认项。不能因为生成了目录树，就宣称已经分析了全部源码。
