## 1. 两种注释模式

**模式 A：功能分块注释（默认）。** 在重要逻辑段前说明该段目的、输入输出和关键步骤。对核心类、公共接口、复杂函数增加职责注释。

**模式 B：逐行讲解（可选）。** 对用户指定的核心文件解释大部分有理解价值的语句。重点解释算法、状态变化、单位/坐标变换、并发同步、内存生命周期、异常处理和关键参数。简单赋值、显而易见的 getter/setter 不需要机械加注释。

默认先生成独立注释说明或 annotated copy。只有用户明确要求“原地修改”时，才直接改源文件。

## 2. 功能分块注释

推荐按逻辑阶段划分，例如：

```cpp
// ============================================================
// 模块：机器人状态估计
// 功能：融合传感器输入，更新当前姿态和运动状态
// 输入：IMU、关节反馈
// 输出：状态估计结果
// ============================================================

// -------------------- 1. 读取传感器数据 --------------------

// -------------------- 2. 更新状态估计 --------------------

// -------------------- 3. 发布状态信息 --------------------
```

注释要描述“为什么有这一步、这一步完成什么”，而不只是复述函数名。分块标题应与真实代码边界一致，不要为了整齐随意拆分。

## 3. 类和函数注释

对重要类说明职责、拥有的状态、协作对象、线程/生命周期约束。对重要函数说明：

- 目的和副作用；
- 输入参数、单位、坐标系、有效范围；
- 返回值或输出；
- 调用前置条件和失败行为；
- 是否阻塞、是否线程安全、是否修改共享状态（仅在源码可确认时说明）。

C++ 可采用项目现有的 Doxygen 风格；Python 可采用项目已有 docstring 风格。优先遵守仓库原有规范，不强行统一风格。

## 4. 逐行讲解模式

适合核心算法文件、复杂控制逻辑、状态估计、规划搜索、训练循环和部署接口。解释应围绕理解障碍，不要给每行都写同义注释。

例如：

```cpp
// 位置误差：目标关节角减去当前测量关节角
const auto error = q_desired - q;

// PD 控制：位置误差产生恢复力矩，速度项提供阻尼
const auto torque = kp * error - kd * dq;
```

如果公式、单位或符号不能从代码和上下文确认，先查定义和调用处，不要猜。涉及 Eigen 表达式、模板推导、指针所有权、异步回调等内容时，应优先解释容易误解的语义。

## 5. 修改保护与验证

原地修改前：

1. 查看 Git 状态和目标文件 diff。
2. 只处理用户指定的第一方源码。
3. 不改算法、变量、控制流、格式和接口。
4. 不覆盖用户未提交的更改。
5. 注释不能改变字符串字面量、宏、预处理条件或代码行为。
6. 修改后检查 diff，确认改动只包含注释。
7. 对可构建项目，尽可能运行原有最小构建或测试；若未运行，明确说明。

不要注释第三方依赖、生成文件、minified 文件、自动生成消息、模型导出代码、构建目录或数据文件。发现原注释错误时，不要静默改写；说明问题并征求是否修订。
